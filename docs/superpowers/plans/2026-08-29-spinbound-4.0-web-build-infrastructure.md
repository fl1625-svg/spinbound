# SPINBOUND 4.0 Web Build Infrastructure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce one authoritative Unity 6.3 WebGL build path that runs tests, generates the playable scene, builds a release Web player, uploads a downloadable artifact, and can publish the same build to GitHub Pages for browser play.

**Architecture:** Unity remains the single gameplay/presentation source of truth. GitHub Actions uses GameCI v4 to run Unity EditMode tests and invoke a project-owned static CI build method. That build method generates the vertical-slice scene, applies Web release settings, and calls `BuildPipeline.BuildPlayer`; the resulting directory is uploaded both as a normal artifact and, on the main branch/manual deploy, as a Pages artifact.

**Tech Stack:** Unity 6000.3.18f1, URP 17.3, Unity Test Framework 1.5.1, GameCI unity-test-runner@v4 and unity-builder@v4, GitHub Actions, GitHub Pages.

**Spec:** `SPINBOUND-4.0-DESIGN-SPEC.md`

## Global Constraints

- Unity 6.3 LTS + URP remains the authoritative production engine.
- Web build must use the same source, simulation, collision, camera, scene and presentation code as the formal game.
- No independently reimplemented browser gameplay mirror.
- Authoritative simulation target remains 120 Hz.
- Web release must preserve gameplay geometry, collision, camera geometry, rotor visibility, hazard timing, and input behavior across quality tiers.
- Actual Unity compilation, tests, Web build and browser runtime are mandatory release gates; source-only checks never substitute for them.
- Release Web compression target is Brotli with data caching enabled and decompression fallback disabled for correctly configured HTTPS hosts.
