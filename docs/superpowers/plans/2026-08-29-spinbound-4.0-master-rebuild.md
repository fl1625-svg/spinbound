# SPINBOUND 4.0 Master Rebuild Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild SPINBOUND from the approved 4.0 design into a production-quality World 1 vertical slice that preserves precision rotating-bar gameplay, adds a default bird's-eye/free 3D camera, uses authored hook-driven stages, and passes real CrazyGames Web quality gates.

**Architecture:** Keep the Unity 6.3 LTS + URP project foundation and the pure C# deterministic core, but replace the 3.0 gameplay semantics above the collision primitives. The implementation is split into six independently testable subplans so physics, camera, level authoring, content production, meta/audio/UI, and release engineering can be reviewed separately. World 2 is blocked until all World 1 gates pass.

**Tech Stack:** Unity 6000.3.18f1, URP 17.3.0, Input System 1.14.2, Cinemachine 3.1.5 only where useful for non-authoritative presentation, NUnit / Unity Test Framework 1.5.1, UGUI 2.0.0, Web build target for CrazyGames.

**Spec:** `docs/superpowers/specs/2026-08-29-spinbound-4.0-design.md`

## Global Constraints

- Authoritative gameplay is 2D XZ and runs at exactly 120 Hz fixed step.
- Base rotor angular velocity target is approximately 60 degrees/second; player cannot directly rotate or stop it.
- Speed tiers are 1.0x / 1.5x / 2.0x with normalized diagonal movement.
- Standard Adventure starts with 3 hearts; damaging collision costs one heart and adds +3.00 seconds.
- Standard Adventure has no automatic checkpoint respawn; zero hearts fails the stage and retry is immediate.
- Start Zone rotation is active while the timer remains stopped until the rotor center exits.
- Heart Zones refill hearts and act as safe recovery/phase-planning spaces; they are not death checkpoints.
- Rotation Springs invert CW/CCW and may apply deterministic phase impulse.
- Default camera is a high bird's-eye perspective near 78 degrees pitch; player may orbit/zoom freely without altering simulation truth.
- Camera-relative controls must always map W/Up to screen up, S/Down to screen down, A/Left to screen left, D/Right to screen right.
- Every normal stage has one memorable hook and follows Introduce → Develop → Twist → Finale where appropriate.
- Critical hazards are deterministic; presentation randomness cannot change gameplay outcomes.
- Presentation geometry is separate from clean gameplay collision geometry.
- No Nintendo characters, maps, layouts, models, textures, music, sound effects, UI, icons, branding, dialogue, or other expressive assets may be copied.
- Desktop High target is 60 FPS; mainstream mobile Medium targets 50–60 FPS; weak Low prioritizes stable 30 FPS.
- Initial playable compressed payload target is approximately 15–25 MB where practical.
- No prototype browser art/audio is accepted as production reference.
- All gameplay changes follow RED → GREEN → REFACTOR; do not accept source-level checks as proof of Unity/Web runtime behavior.

## Execution order and hard gates

1. **Plan A — Core Gameplay Rebuild**: deterministic simulation, reference-calibrated wall response, hearts/timer/zones, springs, dynamic hazard contract.
2. **Plan B — Bird's-eye Camera & Input**: camera-relative movement, free orbit/zoom, Classic View, Tactical View, occlusion, mobile controls.
3. **Plan C — Level Authoring, Solver & Training**: stage data model, phase-aware verification tooling, Training 1–5, Practice/Demo/Ghost foundation.
4. **Plan D — World 1 Production Slice**: World 1 stages, Skill Trial, boss/set-piece proof, Rotor hero asset, environment kit, visual/VFX production pass.
5. **Plan E — Meta, Audio & UI**: Orbit Cores, results/mastery, 3D diorama world map, dynamic music/SFX, HUD/settings/accessibility.
6. **Plan F — Web Release & QA**: CrazyGames lifecycle, Web build, performance budgets, mobile QA, release gate.

A subplan cannot begin its dependent production content until its preceding hard gate is green. Parallel work is permitted only for presentation assets that do not affect authoritative rules.

## Baseline project map

Existing reusable foundations:

- `Assets/SPINBOUND/Core/Runtime/Collision/*` — keep geometry/math ideas; extend collision result to provide contact truth.
- `Assets/SPINBOUND/Core/Runtime/Simulation/*` — replace 3.0 state/tier semantics with 4.0 state and dynamics.
- `Assets/SPINBOUND/Core/Runtime/Gameplay/*` — replace checkpoint-centric flow.
- `Assets/SPINBOUND/Platform/Runtime/*` — preserve platform abstraction.
- `Assets/SPINBOUND/Presentation/Runtime/Quality/*` — preserve/evolve quality-tier structure.
- `Assets/SPINBOUND/Art/Shaders/*` — use as shader prototypes only; must pass the production visual gate before release.
- `Assets/SPINBOUND/Editor/*` — replace W01-01-specific builders with stage/world authoring builders.

3.0 items that are explicitly obsolete:

- `CheckpointSnapshot.cs` and checkpoint-respawn semantics.
- `MovementTier.Precision/Fast/Turbo` naming and UX.
- `PrecisionCameraRig.cs` as the primary gameplay camera.
- `Worlds/Runtime/W01/DaisyHighlands/W01_01CourseDefinition.cs` gameplay geometry.
- `W01_01ReferenceRoute.cs` as the World 1 route truth.
- Daisy Highlands environment content as a production-quality reference.

## Milestones

### M0 — Migration baseline

Exit criteria: spec marked approved; project compiles before gameplay replacement; 3.0 obsolete assumptions are documented; no production code has been deleted before replacement tests exist.

### M1 — 4.0 Core Green

Exit criteria: 120 Hz determinism, speed ratios, automatic rotation, reference-calibrated collision impulse/recovery, +3.00 s penalty, 3 hearts, invulnerability/contact handling, Start/Heart/Safe zones, Springs, fail/retry all pass EditMode tests.

### M2 — Camera Green

Exit criteria: default 78-degree bird's-eye, 360-degree yaw, legal pitch/zoom, Home reset, Classic View, Tactical pause, camera-relative input at 0/90/180/270 yaw, and camera changes do not alter authoritative state.

### M3 — Authoring Green

Exit criteria: stage definitions are data-driven; solver validates at least one no-damage authored reference route; Training 1–5 teach the approved concepts; Practice section anchors and ghost playback work.

### M4 — World 1 Gameplay Green

Exit criteria: World 1 normal stages each pass Kururin Test + 3D World Test; each has a no-damage route; one Skill Trial and one evolving set-piece stage are playable; no blind hazards or impossible timing windows.

### M5 — Production Green

Exit criteria: final-quality representative Rotor, environment kit, lighting, VFX, audio, HUD/results, and world-map presentation pass visual/audio/UI gates. Placeholder assets are absent from the release branch.

### M6 — Web Release Green

Exit criteria: actual Web build loads in supported browsers, CrazyGames lifecycle calls are correct, focus/pause/mobile controls work, representative devices meet performance targets, and package/server compression behavior is verified.

## Execution environment

On a Windows machine with Unity installed through Hub, set once per shell:

```powershell
$env:UNITY_EXE = 'C:\Program Files\Unity\Hub\Editor\6000.3.18f1\Editor\Unity.exe'
```

Canonical EditMode command:

```powershell
& $env:UNITY_EXE -batchmode -nographics -projectPath $PWD -runTests -testPlatform EditMode -testResults TestResults/editmode.xml -quit -logFile Logs/editmode.log
```

Canonical PlayMode command:

```powershell
& $env:UNITY_EXE -batchmode -projectPath $PWD -runTests -testPlatform PlayMode -testResults TestResults/playmode.xml -quit -logFile Logs/playmode.log
```

If Unity is not available in the execution environment, pure C# source/numeric checks may be run, but the milestone remains **UNVERIFIED** until the Unity commands above run successfully.
