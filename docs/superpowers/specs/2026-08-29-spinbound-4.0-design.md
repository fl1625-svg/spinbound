# SPINBOUND 4.0 — Design Specification

**Status:** APPROVED — user confirmed 2026-08-29  
**Date:** 2026-08-29  
**Target:** CrazyGames / desktop + mobile web  
**Engine:** Unity 6.3 LTS + URP  
**Design DNA:** precision rotating-bar navigation inspired by the core interaction logic of *Kuru Kuru Kururin* + world/level design principles inspired by *Super Mario 3D World* + original premium stylized 3D production.

> This project may study gameplay principles and production methods, but must not copy Nintendo characters, names, maps, layouts, models, textures, music, sound effects, UI, dialogue, icons, branding, or other expressive assets. All production content is original.

---

## 0. Executive Direction

SPINBOUND 4.0 replaces the 3.0 design direction wherever they conflict.

The product is no longer designed as a generic 3D obstacle-course game. Its foundation is a deterministic precision-navigation game where the player controls only the center position of an automatically rotating horizontal rotor. The challenge comes from rotor phase, timing, movement speed, route geometry, recovery spaces, direction-changing devices, and deterministic moving hazards.

The 3D layer exists to make the world feel premium, alive, readable, memorable, and commercially competitive without changing the precision rules underneath.

The macro game structure uses compact, highly authored stages, each built around a memorable gameplay hook. Worlds are connected through playable 3D diorama maps with branches, secrets, trials, bonus stages, collectible-driven optional routes, and large set-piece boss stages.

### 0.1 Hard Pillars

1. **Original-core fidelity:** automatic rotor rotation, planar center movement, three movement speeds, phase/timing mastery, wall interaction, healing areas, direction-changing devices, practice/demo/route-learning concepts.
2. **One strong hook per stage:** Introduce → Develop → Twist → Finale.
3. **Default bird's-eye readability:** gameplay must be immediately readable from the recommended high bird's-eye camera.
4. **Free 3D camera:** players may orbit and zoom without changing simulation truth or collision difficulty.
5. **Premium stylized 3D:** commercial-quality art direction, lighting, animation, VFX, UI, audio, and environmental response.
6. **Deterministic gameplay:** same state + same input = same outcome. No random critical hazards.
7. **Web-first production:** 60 FPS desktop target, scalable mobile/low-tier modes, disciplined package size and draw-call budgets.
8. **Short retry loop:** failure-to-retry must be nearly immediate.

# 1. Authoritative Gameplay Model

## 1.1 Simulation Space

Authoritative gameplay occurs on a 2D XZ plane.

State includes:

- rotor center X/Z position
- rotor world-space angle
- rotation direction (CW/CCW)
- current angular velocity / collision impulse state
- current movement speed tier
- heart count
- stage timer and penalties
- deterministic moving-hazard states
- stage trigger states

The presentation layer may contain terrain elevation, bridges, cliffs, buildings, vegetation, waterfalls, particles, clouds, machines, and other 3D content, but those do not redefine the planar collision truth unless a future explicitly separated special-stage ruleset is approved.

## 1.2 Rotor

The rotor is the hero gameplay object and hero visual asset.

Base state:

- automatic continuous rotation
- base angular velocity target: approximately 60 degrees/second
- player cannot directly rotate the rotor
- player cannot stop rotor rotation
- player cannot freely alter angular velocity
- collision/spring systems may temporarily perturb angular velocity or invert direction according to authored rules

The player controls only:

- center movement direction
- movement speed tier
- camera observation

## 1.3 Movement Speeds

Three speed tiers preserve the original interaction logic:

- **Speed 1:** 1.0x movement speed; no accelerator held
- **Speed 2:** 1.5x; one accelerator held
- **Speed 3:** 2.0x; both accelerators held

Desktop default:

- movement: WASD / arrow keys
- accelerator A: Shift
- accelerator B: Space
- Shift or Space = Speed 2
- Shift + Space = Speed 3

Mobile:

- left virtual stick = movement
- right-side A/B buttons = speed tiers

Diagonal input is normalized so diagonal movement is not faster than cardinal movement.

## 1.4 Camera-relative Movement

Movement direction is screen-relative, not fixed world-relative.

At all allowed gameplay camera yaws:

- W / Up = screen up
- S / Down = screen down
- A / Left = screen left
- D / Right = screen right

Camera forward/right are projected onto the XZ plane and normalized before converting screen input to world movement.

The camera never changes simulation geometry, rotor angle, timer, hazard state, collision radius, or leaderboard eligibility.

# 2. Collision, Damage, Recovery, and Advanced Skill

## 2.1 Collision Philosophy

Wall contact is not implemented as simple "movement rejected" logic. It is a deterministic gameplay interaction.

A damaging collision can:

- remove one heart
- add a fixed time penalty (baseline design target: +3.00 s)
- produce a brief center-position knockback
- perturb rotor angular velocity/phase
- recover smoothly toward the base angular velocity target

The exact impulse curve must be tuned against reference-feel tests, not guessed from visuals.

## 2.2 Hearts

Standard Adventure stage:

- starts at 3 hearts
- damaging collision removes 1 heart
- at zero hearts the stage fails
- stage restart is immediate
- no automatic checkpoint respawn in standard Adventure

## 2.3 Heart Zones

Heart Zones:

- refill hearts to full
- function as pacing boundaries between stage sections
- are safe recovery/phase-planning spaces
- may allow deliberate wall contact without normal damage/penalty when explicitly authored as a safe zone
- become Practice Mode section anchors

They are not standard death checkpoints.

## 2.4 Start Zone

At stage start:

- rotor rotation is active
- stage timer has not started
- player can wait for a preferred phase
- stage timer begins when the rotor center exits the Start Zone

This preserves timing strategy at the beginning of a run.

## 2.5 Safe Rotation Areas

A Safe Rotation Area is large enough for a full 360-degree rotor rotation without contact.

Purpose:

- give players a breathing point
- allow observation and planning
- allow phase realignment
- create tension/release rhythm

It is not automatically a healing or checkpoint zone.

## 2.6 Rotation Springs

Rotation-changing devices invert long-term rotation direction (CW ↔ CCW) and may also apply a deterministic phase impulse.

Stage design may use:

- mandatory springs
- optional optimization springs
- phase-control springs
- advanced routes that skip a spring

Springs must communicate state change visually and audibly without requiring text instructions.

## 2.7 Advanced Collision Strategy

The system should support advanced play where deliberate contact can alter phase at a cost. This is allowed only if:

- the behavior is deterministic
- risk/reward is understandable
- it does not become mandatory for ordinary completion
- it remains readable and fair

# 3. Camera System

## 3.1 Default Camera

Recommended default gameplay view:

- high bird's-eye perspective
- target pitch baseline: approximately 78 degrees
- recommended yaw is stage-authored for best route readability
- low-perspective / small-FOV presentation to approach orthographic clarity while retaining real 3D depth

Initial FOV target range: approximately 30–34 degrees; exact final value is a tuning parameter.

## 3.2 Player Camera Freedom

Gameplay camera supports:

Desktop:

- RMB drag: orbit
- mouse wheel: zoom
- Q/E: yaw rotation
- Home: reset to recommended camera

Mobile:

- right-side camera gesture area / multi-touch orbit
- pinch zoom
- visible small Reset Camera action

Allowed target ranges:

- pitch: approximately 35–88 degrees
- yaw: 360 degrees
- zoom: approximately 0.65x–1.6x relative range

## 3.3 Classic View

Settings may expose a Classic View:

- near-top-down pitch
- orthographic or near-orthographic rendering
- same simulation and leaderboard eligibility

This is a comfort/readability option, not an easier physics mode.

## 3.4 Follow Rules

Gameplay camera:

- does not follow rotor rotation
- does not automatically yaw toward movement
- uses a restrained soft dead zone
- uses minimal speed-sensitive look-ahead
- uses very restrained camera shake
- prioritizes rotor endpoint visibility over cinematic movement

## 3.5 Occlusion

Presentation meshes may fade/dither if they obscure the rotor or critical playable path.

Occlusion protection covers:

- full rotor length
- safety margin around endpoints
- near-future route visibility

Gameplay collision geometry itself must remain readable and must not be hidden by the occlusion system.

## 3.6 Tactical View

A Tactical View pauses authoritative simulation and timer, elevates the camera, and allows free inspection of the stage.

It may identify:

- start
- Heart Zones
- Springs
- major deterministic mechanisms
- goal

It should not automatically reveal complete optimal routes unless Demo mode is activated.

# 4. Level Design System

## 4.1 Design From Rotor Solution First

Stages are not authored as ordinary racetracks and then tested afterward.

For every important obstacle segment, the designer must define:

- entry phase
- allowed phase window
- intended speed tier(s)
- center trajectory
- exit phase
- safe solution
- skilled solution
- optimization opportunity where appropriate

The presentation mesh is built around validated gameplay geometry, not the reverse.

## 4.2 Reusable Gameplay Modules

Core module library includes:

- Straight Gate
- Long Narrow
- Wide L
- Tight L
- S Bend
- U Turn
- Waiting Pocket
- Offset Gate
- Double Gate
- Spring Corner
- Moving Gate
- Hazard Lane
- Safe Rotation Area
- Heart Zone transition

Advanced modules are composed only after their component concepts have already been taught.

## 4.3 Phase Chaining

A strong stage segment should frequently allow the exit phase of one challenge to affect the optimal solution of the next.

This creates mastery beyond simple obstacle clearance.

## 4.4 Difficulty Philosophy

Difficulty must come from understandable combinations of known rules, not hidden collision, randomness, unreadable timing, camera occlusion, or arbitrary precision spikes.

Every stage must satisfy:

**Readable → Predictable → Executable → Optimizable**

## 4.5 Stage Tension Curve

Stages need breathing rhythm:

- introduction
- rising challenge
- relief / safe planning
- escalation
- Heart Zone / section boundary where appropriate
- final combination
- goal

Not every stage requires all nodes, but sustained maximum tension is prohibited.

## 4.6 Deterministic Hazards

Critical moving hazards use deterministic cycles.

Randomness is permitted for non-gameplay presentation such as:

- foliage
- ambient creatures
- particles
- clouds

Critical hazard randomness is prohibited.

## 4.7 Solver and Authoring Validation

A level-validation tool must be developed to simulate authoritative rules and catch invalid geometry.

Validation targets include:

- existence of at least one no-damage solution
- route clearance
- impossible timing windows
- dead-end phase states
- sudden precision spikes
- camera-occlusion failures
- unsafe spawn/reset states

Later versions should search multiple starting phases, speed tiers, directions, and route options.

# 5. Stage Design Philosophy — One Memorable Hook

Every normal stage needs a player-describable hook.

Examples of valid descriptions:

- "the stage with opening flower bridges"
- "the stage inside the giant wind engine"
- "the triple spring reversal stage"

If the stage can only be described as "the same corridor but narrower," it fails the hook test.

## 5.1 Hook Structure

Default structure:

1. **Introduce** — safe presentation of the idea
2. **Develop** — require the player to use it
3. **Twist** — alter one condition or combine with one known concept
4. **Finale** — short, memorable culmination

One stage does not need to introduce many unrelated mechanics.

## 5.2 Ten-Second Identity Rule

Within approximately the first 10 seconds, the player should understand the visual/gameplay identity of the stage.

# 6. Training, Adventure, Practice, Trials

## 6.1 Training

Five short training stages are the initial target:

1. automatic rotation + center movement
2. waiting for a useful phase / Straight Gate
3. three movement speeds
4. L-bend / endpoint awareness
5. S-bend + Heart Zone / combined fundamentals

Tutorial text is minimized. Geometry, animation, sound, and staging teach whenever possible.

## 6.2 Adventure

Adventure uses short, authored stages with low retry friction.

Target time envelope:

- first clear: roughly 45–90 seconds for ordinary stages
- practiced run: roughly 30–60 seconds
- expert run: roughly 20–45 seconds

These are targets, not absolute limits.

## 6.3 Practice Mode

For cleared stages, players can practice from:

- Start
- Heart 1
- Heart 2
- etc.

Practice focuses on section mastery rather than normal Adventure failure pressure.

## 6.4 Demo and Ghosts

Supported concepts:

- Developer Demo / successful route demonstration
- Developer Ghost
- Personal Best Ghost
- future leaderboard ghost support if platform/technical constraints permit

Ghosts are non-colliding presentation entities and must never affect authoritative simulation.

## 6.5 Skill Trials

Short 5–20 second technique challenges.

Examples:

- Corner Trial
- Triple Gate
- Reverse Rhythm
- Needle Run

Potential medal targets:

- Bronze
- Silver
- Gold
- Platinum

# 7. World Map and Macro Structure

## 7.1 Playable 3D Diorama Map

World selection is a playable 3D map, not a flat level-selection menu.

The map can contain:

- ordinary stages
- branching routes
- secrets
- Skill Trials
- Bonus stages
- boss/set-piece stages
- collectible-gated optional paths
- environmental changes after clears

The map itself responds to player movement and progression.

## 7.2 World Structure Target

A full world target may contain approximately:

- 5–6 normal themed stages
- 1 high-difficulty main stage
- 1–2 trials / bonus nodes
- 1 boss or large set-piece stage

Exact counts can vary according to content quality.

## 7.3 Launch Scope Discipline

The initial vertical-slice milestone is not the full commercial release.

First production proof:

- 5 Training stages
- complete World 1
- one world map
- one boss/set-piece proof
- core collectibles / results / practice / camera / audio systems sufficient to validate the product

Only after this passes quality gates should Worlds 2+ be produced at scale.

Initial long-form concept set:

Visual: bright highland garden, flowers, soft cliffs, waterways, playful garden structures.  
Gameplay: fundamentals, phase reading, L/S bends, speed selection.

## World 3 — Crystal Caverns

Gameplay: rotation reversal, phase manipulation, tighter spatial puzzles.

## World 4 — Cloudworks

Visual: cloud sea, sky machinery, suspended structures.  
Gameplay: high-speed windows and long committed passes.

## World 5 — Tidal Gardens

Visual: water city / garden hydraulics.  
Gameplay: route state changes, gates, moving channels.

## World 6 — Clockwork Metropolis

Visual: precision mechanical city.  
Gameplay: synchronized cycles, advanced phase chains.

## World 7 — Starlight Observatory

Visual: night sky, astronomical machinery, star-track structures.  
Gameplay: advanced combination and mastery.

## Final / Secret Worlds

Remix known concepts in new relationships rather than merely narrowing every corridor.

# 9. Collectibles, Secrets, and Completion

## 9.1 Orbit Cores

Working collectible name: **Orbit Core**.

Target: up to three per ordinary stage.

Acquisition categories may include:

- exploration route
- skill route
- mastery condition

Collectibles should not merely sit in arbitrary corners; they should reinforce rotor movement, phase choice, or route discovery.

## 9.2 Completion States

Working completion taxonomy:

- CLEAR — complete the stage
- PERFECT — zero damage
- MASTER TIME — beat authored target time
- CROWN — complete mastery package (e.g. all Orbit Cores + Perfect + Master Time)

Exact labels may change during UX/brand pass.

## 9.3 Optional Progression

Collectibles primarily unlock optional content:

- secret branches
- bonus stages
- advanced trials
- cosmetic rewards
- hidden world / expert stages

Ordinary players should not be aggressively blocked from main progression.

## 9.4 Secret Exits

Secret routes are visually motivated and mechanically discoverable.

Examples:

- path behind waterfall
- route requiring a specific spring state
- narrow phase-dependent side passage
- path readable from Tactical View

No arbitrary invisible-wall secrets.

---

# 10. Boss / Set-Piece Design

Boss stages are not conventional health-bar fights.

They are large evolving rotor-navigation mechanisms.

A boss stage may:

- reveal a giant machine from the world map
- change maze geometry in deterministic phases
- synchronize large moving structures
- introduce one high-level transformation of the world's main mechanic
- culminate in a final navigation sequence

The player wins by mastering the stage system, not repeatedly hitting an enemy.

Boss reveal cinematics are short and gameplay-focused.

# 11. Premium Stylized 3D Art Direction

## 11.1 Visual Goal

**Premium Stylized 3D**:

- strong silhouettes
- clean large forms
- polished bevels and curves
- stylized PBR materials
- sophisticated lighting
- strong gameplay contrast
- restrained effects
- responsive environment

Not photorealism, low-poly placeholder art, asset-store collage, or bloom-heavy mobile-game rendering.

## 11.2 Visual Hierarchy

Priority order:

1. Rotor
2. gameplay walls / hazards / interaction devices
3. traversable route and safe spaces
4. environment decoration
5. distant scenery

Art must never make layer 4 or 5 compete with layers 1–3.

## 11.3 Shape Language

Each world defines a coherent shape language in addition to a palette.

Examples:

- Daisy Meadow: rounded organic forms / petals / soft terrain
- Windmill Woods: discs / spokes / timber structures
- Crystal Caverns: faceted prisms / sharper silhouettes
- Clockwork Metropolis: rings / rails / mechanical plates

## 11.4 Gameplay vs Presentation Geometry

All critical geometry has:

- clean invisible gameplay collision representation
- separate higher-detail presentation mesh

Decorative details must not create surprise collisions.

## 11.5 World Depth

Every production stage uses layered depth:

- foreground
- gameplay island/layer
- midground
- background
- sky / atmosphere

Background motion and atmospheric perspective prevent the world from feeling like a flat test board.

# 12. Rotor Hero Asset

The Orbital Explorer is treated like a character-level hero asset.

Potential material families:

- ceramic shell
- brushed metal
- dark mechanical internals
- energy glass
- restrained emissive elements

Presentation-only motion may include:

- internal counter-rotation
- energy-core animation
- speed-tier mechanical response
- subtle hit deformation/recoil
- healing/recharge response

None of these alter authoritative collision geometry.

Rotor must remain clearly readable over every world palette.

# 13. Lighting, Materials, Shaders, and VFX

## 13.1 Lighting

Use stylized cinematic lighting rather than photoreal brute force.

Typical world setup:

- authored key light
- cooler/warmer fill contrast as appropriate
- baked GI for static environments
- Light Probes
- Reflection Probes
- clear contact shadows
- gameplay-oriented rim/readability treatment for Rotor

## 13.2 Shader Families

Maintain a small coherent set:

- Stylized Environment PBR
- Foliage
- Water
- Rotor Hero
- Energy / VFX

Avoid uncontrolled per-asset shader proliferation.

## 13.3 Bloom and Post

Bloom is restrained and reserved mainly for energy/reward content.

Post-processing should preserve clarity. Strong motion blur, excessive chromatic aberration, and gameplay-obscuring depth of field are prohibited during precision play.

## 13.4 VFX Hierarchy

VFX intensity tiers:

- ambient
- movement
- interaction / near-miss
- damage / healing
- reward / goal / boss clear

Not every action deserves a screen-filling effect.

## 13.5 Near Miss

Near-miss detection provides subtle high-skill feedback when a rotor endpoint passes close to a wall without contact.

Feedback may include:

- short air-cut / whoosh sound
- restrained trail/disturbance VFX

This must not affect physics.

# 14. Environmental Responsiveness

The world should feel reactive without becoming noisy.

Potential reactions:

- foliage bends or shakes near movement
- flowers react to nearby rotor passage
- leaves/dust respond to high speed
- water produces stylized ripples/splash cues
- mechanisms react to progression
- world-map paths animate/unlock visibly
- goal/Heart areas activate their surrounding environment

These systems are scalable by quality tier.

# 15. Audio Direction

Prototype audio is not production reference.

Production audio is divided into:

- music
- gameplay SFX
- world ambience
- UI
- musical stingers

## 15.1 Dynamic Music

World music should be original and state-responsive.

Potential synchronized stems:

- Base
- Rhythm
- Motion
- Finale / event layer

Transitions are musically synchronized and smoothly mixed.

## 15.2 World Audio Identity

Each world has its own instrument and texture palette while remaining part of one SPINBOUND score identity.

## 15.3 Rotor Audio Identity

Rotor sound set includes:

- core hum
- rotation air
- movement layer
- Speed 2 layer
- Speed 3 layer
- near miss
- collision
- spring interaction
- healing/recharge

Speed changes should use layered/crossfaded design, not naive pitch scaling.

## 15.4 Surface-aware Impacts

Collision audio may blend a shared gameplay impact with surface-dependent layers:

- stone
- wood
- metal
- crystal
- other world-specific materials

Impact intensity also varies by contact severity.

## 15.5 Spatial Audio

Use spatial audio where world position matters (waterfalls, large mechanisms, boss machinery). Critical player feedback should remain consistently readable regardless of camera yaw.

# 16. UI / UX

## 16.1 Gameplay HUD

Default HUD is minimal:

- hearts
- timer
- collectible state
- small speed-state indicator if needed

No mandatory minimap, giant progress bar, mission text stack, or dense mobile-style chrome.

## 16.2 Mobile Controls

- left virtual stick
- right A/B speed buttons
- separate camera interaction region
- compact Reset Camera control

Important play space remains unobstructed.

## 16.3 Main Menu

Main menu is presented over a live 3D world/map scene rather than a generic static background.

Working primary actions:

- Play
- Challenges
- Settings

## 16.4 World Map Stage Interaction

Approaching a stage node reveals a compact information panel with:

- stage name
- collectible status
- best time
- mastery status

UI disappears when not needed.

## 16.5 Results

Results are fast and replay-oriented.

Show:

- time
- damage/perfect state
- collectible count
- Master Time result

Primary actions:

- Retry
- Next
- Map

Failure-to-retry and result-to-retry must be very fast.

# 18. Performance and Web Budgets

## 18.1 Simulation

Authoritative simulation target: 120 Hz fixed step.

Render frame rate does not change collision truth.

## 18.2 Frame Rate

Targets:

- desktop High: 60 FPS
- mainstream mobile Medium: target 50–60 FPS
- weak hardware Low: stable 30 FPS prioritized over effects

## 18.3 Quality Tiers

Quality may scale:

- vegetation density
- shadow resolution/distance
- AO
- reflections
- particle density
- environmental interaction
- distant detail

Quality must not scale:

- gameplay geometry
- collision
- camera geometry
- rotor visibility requirements
- hazard timing
- input behavior

## 18.4 Rendering Discipline

Use as appropriate:

- SRP Batcher
- GPU Instancing
- static batching
- LOD Groups
- occlusion culling
- baked lighting
- lightweight foliage animation

Avoid large numbers of per-object CPU Update loops.

## 18.5 Draw Calls

Initial visible draw-call targets per representative stage:

- High: < ~150–200
- Medium: < ~100–140
- Low: < ~80–100

These are budget targets subject to profiling, not excuses to reduce gameplay clarity.

## 18.6 Download Size

Target fast first-play experience.

Initial playable payload target: approximately 15–25 MB compressed where practical.

Additional worlds should use shared assets and staged/on-demand delivery strategies as compatible with the platform build.

# 19. QA and Quality Gates

A stage is not approved because it merely runs.

## 19.1 Gameplay Gate

- core rules match approved 4.0 behavior
- no-damage route exists
- control directions correct at tested camera yaws
- movement speed tiers deterministic
- collision response correct
- start/heart/spring/safe zones behave correctly
- quick retry works

## 19.2 Level Design Gate

- stage has one clear hook
- Introduce/Develop/Twist/Finale structure works where appropriate
- stage is readable/predictable/executable/optimizable
- no blind hazard or fake difficulty
- pacing contains sufficient relief
- optional mastery path exists where appropriate

## 19.3 Camera Gate

Validate at least:

- default recommended camera
- yaw 0 / 90 / 180 / 270
- several legal pitches/zooms
- Classic View if enabled

Changing camera must not alter authoritative outcome.

## 19.4 Visual Gate

Capture at minimum:

A. recommended high bird's-eye gameplay view — must be immediately readable  
B. lower cinematic free-camera view — world must look premium 3D  
C. Tactical View — stage must read as a coherent attractive diorama

## 19.5 Audio Gate

- no temporary placeholder audio in release branch
- rotor state readable by sound
- hits / springs / healing / goals distinct
- world ambience has coherent identity
- music transitions are clean

## 19.6 Performance Gate

Profile actual Web build on representative desktop/mobile/low-end targets. Source-level budget checks alone are not sufficient.

## 19.7 Release Gate

Validate:

- CrazyGames lifecycle integration
- browser startup
- pause/resume behavior
- focus loss
- mobile touch
- WebGL/Web build compatibility
- loading behavior
- package compression/server compatibility

# 22. Non-Negotiable Product Tests

Every major design decision must pass two conceptual tests:

## Kururin Test

Does this mechanic/stage create an interesting decision involving automatic rotor rotation, phase, center trajectory, timing, or speed choice?

If not, it does not belong in the core Adventure merely because it looks cool.

## 3D World Test

Can a player describe this stage afterward by one memorable visual/gameplay idea?

If not, the stage is too generic or overloaded.

---

# 23. Definition of Success

SPINBOUND 4.0 succeeds when:

- a player who appreciates precision rotating-bar gameplay immediately recognizes the depth of timing/phase navigation without the game becoming a copy of any Nintendo title
- a new player can understand the basic interaction quickly through level design rather than text walls
- each stage feels authored around a specific idea
- the 3D world is visually premium without obscuring collision truth
- the default bird's-eye view is the most comfortable competitive view while free camera remains useful and enjoyable
- short stages produce a strong "one more try" loop
- secrets, mastery goals, ghosts, trials, and world-map progression provide replay depth
- art/audio/UI feel like one coherent original commercial product
- real Web builds meet practical CrazyGames performance and loading constraints

This specification supersedes conflicting SPINBOUND 3.0 design assumptions.
